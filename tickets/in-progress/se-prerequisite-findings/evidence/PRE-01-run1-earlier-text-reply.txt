Investigation is done. I need one decision from you, so I'm holding at Ready for Approval.

**What I found**
- **Header drop:** `createTransport` passes `{ headers }` to the SDK, but `tiny-mcp-sdk` reads only `options.requestInit.headers`. I ran a probe: a server created with `Authorization: Bearer t` came out with `headers: {}`. So no configured header reaches any request today, and a Jira token would never be sent.
- **Test gap:** the unit test replaces the SDK with a fake that checks `opts.headers`, so it passes while the real behavior is broken.
- **Preset:** the repo has no preset mechanism. `mcps.json` holds one `docs` server with empty headers. I'm treating a preset as a ready-made Jira server entry.
- **Branch name:** the repo's branch is `main`, not `master`. I based the work on `main`, in the worktree `/tmp/spf-iso-ws/mini-mcp-jira` on branch `jira-preset`.
- **Real Atlassian host:** it can't be reached, since the URL is an `.example` host. I can only verify the headers the SDK would send.

**Decided by me, within your direction**
- **Header fix:** I'm fixing the header drop in this ticket. It's a one-line change and the "done" condition can't be met without it. I'll also change the test so it uses the real SDK's option shape and fails on the old code.
- **Scope:** OAuth, any UI, other presets and a secret vault are out of scope.

**Needs you: where does the token live?**
- **A:** the token goes literally in `mcps.json` as `"Authorization": "Bearer <token>"`. This is simplest, but `mcps.json` is tracked by git, so a real secret could be committed.
- **B:** the preset holds `"Authorization": "Bearer ${JIRA_API_TOKEN}"`, and the client expands environment variables in header values. If the variable is unset, it fails with a clear error. This keeps the token out of git and costs about 5 lines, limited to header values.

I recommend B, because of the secret-in-git risk.
